## P0 — производительность / узкие места

Найдено при аудите бутылочных горлышек 2026-08-12. Структурные, требуют архитектурных решений, не быстрых патчей.

- [ ] **Глобальная сериализация: 1 RQ-воркер = 1 образец одновременно.** `worker_init.py` поднимает ровно один блокирующий `Worker.work()`, без `--burst`/пула/`replicas` в docker-compose. Сколько бы образцов ни стояло в очереди — обрабатывается строго по одному. При наблюдаемой длительности прогона 1.5–32+ часов это жёсткий потолок пропускной способности всей платформы.
- [ ] **Параллелить некуда физически.** Хост — 64 ядра CPU. `FLYE` в `nextflow.config` запрашивает `cpus = 60` на один образец — почти весь хост под один прогон. Добавить второй параллельный воркер сейчас нельзя, не пересмотрев резервирование ресурсов на процесс (Flye/Kraken2/CheckM и т.д.) — иначе будет драка за одни и те же ядра/память.
- [ ] **Хост реально перегружен соседями, не гипотеза.** `swap` **постоянно** на 100% (8Gi/8Gi), не разово. Чужие проекты на этом же сервере: QuestDB ~30ГБ, chatbot-backend ~20ГБ, vLLM ~7.5ГБ — стабильно, не пиково. Flye (до 120ГБ) и Kraken2 (100ГБ на загрузку базы) конкурируют за ту же физическую память.
- [ ] **Непредсказуемая длительность прогона.** Образцы сопоставимого размера (~5ГБ, `large_samples`) шли от 1ч46м до **32+ часов**. GTDB-Tk отключён (`gtdbtk_db = null`), не при чём. Подозреваются CheckM (бюджет 6ч)/dRep (4ч)/CONCOCT. Общая длительность прогона теперь надёжно пишется (`nextflow_executions.duration`, починено — коммит `da9dcfe4`), но **по стадиям** разбивки всё ещё нет — папки успешных прогонов чистятся после аплоада в MinIO вместе с `nextflow_trace.txt`, так что понять, какая именно стадия виновата, по-прежнему нельзя без отдельного сохранения трейса.
- [ ] **Kraken2 (86ГБ `hash.k2d`) теперь грузится до 3 раз за один прогон** — `KRAKEN2_READS` (добавлен сегодня) + `KRAKEN2_METABAT2` + `KRAKEN2_CONCOCT`, каждый через `--memory-mapping` заново. Работает корректно, но лишняя нагрузка на I/O/память, которую не оптимизировал.
- [ ] **Арифметика беклога**: при пропускной способности "1 образец за раз" и разбросе 2–32ч, полная очистка текущего P1-беклога данных (см. ниже) может занять от нескольких дней до пары недель непрерывной работы.
